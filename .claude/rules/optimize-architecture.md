# `tokenjam/core/optimize/` — the analyzer package

Powers `tj optimize` and the `get_optimize_report` MCP tool. Public API re-exported from
`__init__.py`: `build_report()` (orchestrator), `report_to_dict()`, `ANALYZER_REGISTRY`,
`ANALYZER_ORDER`, plus result dataclasses.

Architecture: `registry.py` holds the `@register("name")` decorator and the `ANALYZER_REGISTRY`
dict; `runner.py` defines `ANALYZER_ORDER` and orchestrates execution; `types.py` holds
`AnalyzerContext` + result dataclasses + `MODEL_DOWNGRADE_CAVEAT`. Individual analyzers live in
`analyzers/`, each as a single file registering via `@register`.

**Analyzers never run on a request path.** Reports are precomputed by a background daemon pass
(`report_store.py` + `scan_cycle.py`) at boot, on an interval, and on `POST /optimize/rescan`;
routes read the stored report.

> **Before touching any analyzer, its persona gating, or any savings/$ derivation, read
> `.claude/product-state/ANALYZER-PERSONA-MATRIX.md` in the meta-repo** — the durable decision
> record (actionable ceiling, the three-gate test, per-analyzer verdicts, number-derivation stance).
> The Critical Rules governing this package live in `.claude/rules/optimize-analyzers.md` (16, 19,
> 26, 29, 31, 39, 40) and `.claude/rules/optimize-cost-figures.md` (22, 27, 28, 30, 32, 41).

## Registry strings vs file names

Registry strings (the user-facing names) and file names are **decoupled** (Critical Rule 19):

- `model_downgrade.py` → `@register("downsize")` — structural candidates behind a small-session gate on input tokens, output tokens and tool-call count (the ceilings are `SMALL_INPUT_TOKENS` / `SMALL_OUTPUT_TOKENS` / `SMALL_TOOL_CALLS` in `model_downgrade.py`; read the constants for values). Never claims quality equivalence — caveat baked into a dataclass default
- `budget_projection.py` → `@register("budget-projection")` — per-provider cycle spend vs `[budget.<provider>]` ceiling; only fires when budget > 0
- `cache_efficacy.py` → `@register("cache")` — current cache-read efficacy per (provider, model)
- `cache_recommend.py` → `@register("cache-recommend")` — Anthropic-only structural prefix detection for `cache_control` placement
- `workflow_restructure.py` → `@register("script")` — `(tool_name, arg_shape)` cluster detection for deterministic-script candidates
- `plan_reuse.py` → `@register("reuse")` — repeated-planning cluster detection; a savings analyzer (carries `past_overspend_usd`). Has a dedicated endpoint/report path (`GET /api/v1/reuse/clusters`, `tj report --reuse`) because its per-cluster planner text can be many KB
- `prompt_bloat.py` → `@register("trim")` — LLMLingua-2 token-significance classification (requires `tokenjam[bloat]` extra)
- `subagent_rightsizing.py` → `@register("subagent")` — per-subagent right-sizing, Claude Code-only (keys off `sub_agent_id`, populated only by CC backfill)
- `batch_placement.py` → `placement` — the Batch API lane; produced INSIDE `downsize` and unregistered, so selection cannot reach it

The live list is `ANALYZER_REGISTRY` / `ANALYZER_ORDER` in `runner.py` — derive it from there rather
than trusting this enumeration. Analyzers receive an `AnalyzerContext` and operate on `db.conn`
directly. To add one: drop a file under `analyzers/`, decorate with `@register("name")`, append to
`ANALYZER_ORDER` if ordering matters — `cmd_optimize`'s positional `findings` Click choices
auto-derive from the registry.

## The per-analyzer dollar-field contract — ONE canonical field, no carve-outs

A cost analyzer's avoidable figure is `past_overspend_usd` / `_tokens` / `_basis`: observed over the analyzed window, past tense, never paced, never discounted, and rendered by every surface. One companion and no others — `coverage_note` on `CostProposal` (words, never a figure, ending by saying the difference is what was NOT analysed). `estimated_recoverable_*`, `estimated_monthly_*`, `observed_cost_*`, `cost_of_waste_*` and `gross_recoverable_*` are RETIRED names: do not reintroduce them on any analyzer or surface, and do not add a fourth name for the same quantity. `cost_proposals.past_overspend_rollup` is the ONLY aggregate — it ships as the `past_overspend` block on `GET /relearn/cost-proposals` and both leading surfaces read it verbatim rather than re-deriving it in JS. `None` means "not measured" and renders an em dash, never `$0`. `estimate_basis` / `estimate_confidence` travel with the figure on every analyzer that carries one and round-trip through `report_to_dict`/`report_from_dict`; the Overview waste band is registry-driven off the PRESENCE of `past_overspend_usd`, so a future analyzer appears with no UI change. Every rule here has a test in `tests/unit/test_past_overspend.py`; the evidence behind them, the per-analyzer verdicts, and the mixed-basis history are recorded in `.claude/product-state/ANALYZER-PERSONA-MATRIX.md` §7 — read them there, and never re-derive them here.

- **No user-facing surface may render a PACED figure.** There is no pacing left in the cost pipeline at all; every figure is the analyzer's own window observation.
- **A headline figure is the CEILING, not the expectation.** Lead with the largest figure the derivation honestly bears; never "correct" it downward with a realization factor, an adoption rate or any other haircut invented at the render layer (founder decision). A ceiling must still be reachable, so a slice the fix **structurally cannot touch** is excluded — that is a correctness fix, not a haircut. One carve-out: where a card offers a fix the user is about to apply, lead with the realized figure instead.
- **WHERE a permanent rule lands changes what it costs to KEEP, never whether it is offered.** `rule_placement.py` resolves which projects incurred a finding (`core/transcript.first_recorded_cwd` → `core/summarize/repo_roots.resolve_roots`), so confining a rule to them lowers its standing cost with no change to the finding. There is no budget left for that lower cost to feed — a rule is offered whenever its card is `apply_capable`, full stop. Two things stay load-bearing. **(a) Two costs, not one:** STANDING follows the sessions, FOOTPRINT follows the FILES — charging either for the other's question makes placement stop being arithmetic. **(b) Unifying the FIX surface must not merge the CLAIMS** (Critical Rule 27): the per-session weight maps are BREAKDOWNS of each analyzer's own `past_overspend_tokens`, split by the same weights on the token and the dollar side so every destination's implied rate equals the finding's own (Critical Rule 28), and a recorded cwd that no longer exists is surfaced in a `coverage_note` as what was NOT analysed (Critical Rule 30) — never reconstructed, never redistributed. `rule_placement.py` is named that, not `placement`, because `placement` is already a registered analyzer name for an unrelated question (the Batch API lane).
- **A rule a card writes must ERASE the number the card found.** `past_overspend_usd` is the maximum its analyzer knows; if applying the fix would leave it roughly where it was, that is a correctness bug, not a UX gap. Two durable halves: the shape-based default-down is the lever and stays, and **a premium escape hatch must be checkable by an outside reader rather than self-assessed** — an agent asked to rate its own task's difficulty answers yes, so the exception swallows the rule. State exceptions as conditions that are either written into the dispatch or not.
- **HOW a rule reaches the agent is a DELIVERY MECHANISM, with its own pricer.** `core/rulewrite/delivery.py` is the seam: a `DeliveryKind` owns its own renderer AND its own pricer, and adding a mechanism is a registration plus two functions — never an edit to the staging, diff, apply, undo or budget machinery, none of which may name a CLAUDE.md. The rung ladder grades intervention STRENGTH, not delivery, so "does this put tokens in front of the model" is asked of `DeliveryKind.carries_prompt_text` and never inferred from the rung: a `UserPromptSubmit` re-injection or `PreToolUse` `additionalContext` nudge is prompt text on a different SCHEDULE, lands in the conversation, and is re-sent on every subsequent turn — so it may not price to zero the way an executed formatter or guard hook does. An unknown mechanism is REFUSED rather than falling back to markdown; a wrong write to a real file is the one failure the lifecycle exists to prevent.
- **A generated hook carries three rails that are not interchangeable with a rule's.** `additionalContext` MUST be nested inside `hookSpecificOutput` — at top level it is silently ignored, so the hook runs, exits 0, injects nothing and looks like it worked. The per-session cap lives in the SCRIPT, keyed on the stdin `session_id`, because only `SessionStart` is structurally once-per-session and `once` is honored solely in skill frontmatter, never in a settings file. And injection is advisory, fail-open, never blocking by default — a misfiring blocking hook degrades every session until removed. Hook entries MERGE across settings layers, so a write cannot clobber the user's hooks but also must not assume it is the only writer.
- **A fix the user already dealt with — applied or dismissed — must lose its OFFER and keep its FIGURE** (Critical Rule 32). The ledgers are `cost_applied.json` / `applied_fixes.json` / `dismissed.json` beside the DB: lock-free sinks, deliberately **not** DuckDB tables, because `tj rules` is in `no_db_commands` and must answer while `tj serve` holds the write lock. Resolve through the ONE matcher (`cost_apply.signature_is_applied`, which already treats a legacy agent-only mark as covering the later model-qualified signatures); a second matcher silently reopens every card it settles. Three properties, each a test: **the row STAYS listed** carrying its state (a user who applies something and then sees nothing cannot tell "done" from "broken"); **a dismissal must be REVERSIBLE**, which durability makes non-negotiable; and **an unreadable ledger reads as "nothing applied"**, because that direction only wastes attention while the opposite hides fixes the user never made. Pin it by asserting the whole record is byte-identical with and without the ledger entry EXCEPT the offer fields — an equal-value check passes a figure that got re-derived through a zero.
- **A fix must name an action that EXISTS, for THIS user, through a key the harness actually reads.** A silently-ignored key is worse than no line: it converts an unfixed problem into one the user believes is fixed. A value that cannot be derived from the observation is OMITTED, never guessed — a plausible frontmatter line is indistinguishable from a measured one. No-file is not no-fix: a user or project subagent of the same name overrides a built-in and keeps its own `model`, so offer the CREATE (and watch shape checks around this — a lowercase-only slug predicate silently rejects `Explore` and `Plan`). Gate a fix the persona cannot perform with a **persona check at the point of production** (Critical Rule 26(c)), not a dollar threshold, and withhold only the offer. Fix text that says the harness already handles it is not a placeholder: it carries an explicit `advisory_only` flag, because "no template matched" and "none is needed" are different statements. In every case the observation stands and `past_overspend_*` is untouched.
- **Fix text lives in ONE catalog with a lint, because scattered constants are why the above could happen.** `core/fixes/` holds one `FixRecord` per fix type — text, delivery kind, personas, lever, the observation it answers, and the shapes it may not excuse (`must_not_relicense`) — and every analyzer reads its text from there instead of defining a constant. Two copies of a policy is two policies. `core/fixes/lint.py` checks the properties mechanically, and above all that **a fix may not re-license the behaviour its own analyzer bills for**. Two dimensions a bare string cannot carry: **persona** (a Claude Code user edits instruction files, agent files and hooks; an SDK service edits routing code and redeploys — handing either the other's fix names an action they cannot take) and **lever**, where `model` and `effort` are separate and not substitutes: a worker that did not know enough needs a bigger model, one that did not try hard enough needs more effort.
- **One instruction, one record — and the duplicate check must use CONTAINMENT (`|a ∩ b| / min(|a|,|b|)`), not Jaccard.** Several analyzers can author their own wording of the same rule from different families, and a pairwise text check is the only defence against it. The harm is not untidiness: **length and redundancy reduce adherence**, so writing a rule three times makes it LESS likely to be followed than writing it once. Jaccard divides by the UNION, so it collapses when two texts differ in LENGTH — which is exactly this defect's shape — and would certify the duplicates clean; a check that cannot catch what it was written for is worse than no check, because it reports the problem as absent. The CLAIMS stay disjoint (Critical Rule 27 is untouched); only the instruction is shared, with per-analyzer framing living in the card's advise text rather than in a second copy of the rule.
- **Two surfaces rendering one finding must lead with the SAME fix, through the same helper** (`cost_proposals.compound_offload_fix`), so they cannot drift into different wordings. Related: **`/compact` is never listed as an actionable lever** — it is transient, persists nothing past the session, users who feel a session filling already do it unprompted, and it sits below the actionable ceiling recorded in `.claude/product-state/ANALYZER-PERSONA-MATRIX.md`. Listing it beside durable levers implies it is the same kind of thing and pads a list whose length is itself a cost to adherence; it survives only in an explicitly-labelled "immediate relief in an already-full session" position.
- **A path-scoped rule is not a cheaper way to say the same thing — it is a genuinely cheaper way to carry it.** A `.claude/rules/*.md` carrying a `paths:` glob loads only when Claude reads a matching file, so only its frontmatter is resident, and that near-zero rent is real even though it no longer feeds any offer/suppress decision. Three things are load-bearing. **(a) The frontmatter is the entire reason it is cheap** — a rule in the same directory WITHOUT `paths:` loads at launch with `CLAUDE.md` priority, so `core/summarize/load_semantics.classify` takes the file TEXT and decides on `has_paths_scope`, never on the directory, and the renderer REFUSES a path-scoped kind that emits no globs (the file would be written, the rule would work, and only the cost would be wrong). Accept both YAML forms — a block list's inline value is empty, so an inline-only check reads a good scoped rule as unscoped. **(b) Selection is DERIVED from the LEVER, never preferred** — a rule about the shape of the next action decides something *before any file is read*, so only file-shaped (awareness) fixes may scope, and only when the record names its own globs; inferring a glob from prose is guessing which files an instruction is about. **(c) Brace expansion has a budget** — past it a pattern is used UNEXPANDED and matches nothing, so the rule reads as applied while never firing; refuse such a glob rather than emitting a silent no-op.
- **Ground a behavioural rule in the evidence it came from — by REPLACING vague words, never by appending them.** Four rules. **(a) Substitution, never generation** — a template carrying "you did X in Y" beats both a generic sentence and a model call: no cost, no latency, no new failure mode, and it cannot hallucinate a directory the user does not have. **(b) SPECIFIC MUST NOT MEAN LONGER** — a longer instruction file reduces adherence, the very thing grounding is for, so a substitution REPLACES a vague span and a grounded rendering that came out materially longer is DISCARDED for the generic text (`grounding.MAX_GROUNDED_GROWTH`); the failure mode to guard against is the generic sentence plus an evidence paragraph, which looks like an improvement and is a regression. **(c) Grounding lives in RENDERING, never in the record set** — one catalog record per fix, always; minting a record per user or per finding makes the catalog and its duplicate lint meaningless overnight. **(d) Degrade per-substitution, and never invent specificity** — an unobserved slot skips its own substitution and keeps that generic span, and an empty field means not observed and is never filled with a plausible-looking value. Mechanical fixes are concrete by construction and are deliberately left alone.
- **There is no write budget.** A permanent rule is offered whenever its analyzer marks the card `apply_capable` — no net-of-standing-cost floor, no per-window write cap, no agent-file growth ceiling. Do not reintroduce one under a new name; a `RuleWrite`'s `offered` flag is False only for a rule the user already applied, already has in their own files, or dismissed (`core/rulewrite/plan.py`). Standing-cost PRICING still exists (`core/rulewrite/delivery.standing_tokens_per_session`) and is still real — rung matters (a skill charges only its always-loaded frontmatter; an executed hook/config charges ZERO, but see `carries_prompt_text`, which overrides the ladder for an injecting hook) — but it is purely informational now: `rule_placement.py` still uses it to pick the cheaper destination, and a staged write still carries it for display, but nothing gates an offer on it any more.
- **The same load semantics govern READING a file, not just writing one.** `core/summarize/load_semantics.py` is the single source of truth both sides classify through: a `CLAUDE.md` / `.claude/rules/*.md` is resident in full on every call of every loading session, while a `.claude/skills/*/SKILL.md`, `.claude/commands/*.md` or `.claude/agents/*.md` surfaces only its **frontmatter** that way and delivers its **body** on invocation. So the window figure is two separately-observed terms — `always-resident reduction x sessions x reads per session` **+** `on-demand reduction x OBSERVED invocations` — never one term applied to the whole file. Getting this wrong in either direction is a real defect: pricing a whole skill body as always-resident makes an uninvoked skill library read as the most expensive prompt file a user owns and can push the cross-analyzer token rollup above the window's billed tokens, while pricing an invoked body at zero denies that a long skill that really runs costs anything. The invocation multiplier is OBSERVED from Claude Code transcripts (`core/summarize/invocations.py`: `Skill` tool calls, typed `<command-name>` slash commands, `Task`/`Agent` `subagent_type`), never assumed — and "invoked zero times" (a measurement, prices the body at zero) is a different statement from "no transcript corpus" (not a measurement; Critical Rule 28 corollary (a) degrades BOTH fields).
